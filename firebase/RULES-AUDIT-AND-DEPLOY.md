# مراجعة قواعد Firestore المقدمة وتعديلات الأمان

## الخلاصة
الكود المرسل يصلح كمسودة أولى، لكنه لا ينبغي نشره كما هو. أهم المخاطر:
1. أول حساب يستطيع إنشاء `/config/owner` ويصبح المالك؛ هذا سباق على حساب المالك وليس إثبات ملكية.
2. العميل يستطيع إنشاء طلب بحقول إضافية غير مقيدة، وقد يمرر حقول أسعار/حالة/بيانات مالية لم تكن مقصودة.
3. تحديث مصفوفة `msgs` لا يثبت أن الرسائل القديمة بقيت كما هي؛ يمكن إعادة كتابة التاريخ مع إضافة رسالة واحدة.
4. بيانات التحويل لا تقيّد المبلغ والحقول والحالة والمرجع بما يكفي.
5. السماح للموظف بتحديث مستندات الطلب/التحويل بالكامل يحتاج فصل صلاحيات أدق وتحققًا من انتقالات الحالة.
6. `site/private` مقروء لكل مستخدم مسجل، رغم احتمال احتوائه على إعدادات داخلية أو تفاصيل لا تخص العملاء.
7. نموذج `leads` عام وقابل للإغراق؛ قواعد Firestore لا تنفذ rate limiting.
8. الاعتماد على حقل role داخل ملف المستخدم ممكن فقط إذا كانت قواعد تعديل ذلك الحقل محكمة، لكن الأدوار الأعلى يجب إنشاؤها من بيئة موثوقة لا من التسجيل العام.

## قرارات النسخة المحسنة
- إزالة آلية "أول من يسجل يصبح المالك". أنشئ المالك الأول من Admin SDK/سكريبت موثوق بعد التحقق من هوية المالك.
- التسجيل العام ينشئ دور `client` فقط وبحقول محددة.
- فصل الرسائل في subcollection بدل مصفوفة داخل الطلب/الدعم؛ الرسائل append-only ولا يمكن تعديلها أو حذفها من العميل.
- إنشاء الطلبات والتحويلات وتغيير الحالات المالية عبر Cloud Functions بعد التحقق من ملكية الطلب والقيمة والمرجع والإيصال.
- سجل `ledger` للقراءة المصرح بها فقط، والكتابة عبر الخادم فقط.
- `site/private` للمدير/المالك فقط.
- تخزين خاص بمسارات المستخدمين، مع حد للحجم وأنواع أولية مسموحة. فحص الملفات يجب أن يكون server-side.

## مخطط البيانات المقترح
- `users/{uid}`: بيانات الحساب العامة والدور الذي يدار إداريًا.
- `orders/{orderId}`: uid, productId/serviceId, amount, currency, status, createdAt, updatedAt.
- `orders/{orderId}/messages/{messageId}`: senderUid, senderRole, text, createdAt.
- `transfers/{transferId}`: uid, orderId, amount, reference, receiptPath, status, reviewedBy, reviewedAt.
- `ledger/{entryId}`: uid, type, amount, currency, sourceId, createdAt, createdBy؛ لا يكتب العميل فيه.
- `support/{uid}`: حالة المحادثة والتعيين وبياناتها الإدارية.
- `support/{uid}/messages/{messageId}`: senderUid, senderRole, text, createdAt.

## خطوات النشر الآمنة
1. لا تلصق القواعد قبل مواءمة أسماء الحقول ومسارات التطبيق الفعلية معها.
2. أنشئ المالك الأول من Admin SDK، ولا تسمح للمتصفح بإنشاء role=owner.
3. اختبر المستخدم غير المسجل، العميل، الموظف، المدير والمالك في Firebase Emulator Suite.
4. اختبر محاولات: ترقية العميل لنفسه، قراءة عميل آخر، إنشاء طلب بمبلغ معدل، تزوير رسالة موظف، تعديل رسالة قديمة، اعتماد تحويل من العميل، ورفع ملف تنفيذي.
5. راجع أخطاء القواعد وطلبات التطبيق في Emulator قبل النشر.
6. فعّل App Check وقيود إساءة الاستخدام والتنبيهات والنسخ الاحتياطية.
7. لا تضع مفاتيح Admin SDK أو Cloudinary API Secret في الواجهة. استخدم Cloud Functions/بيئة خادم.

## حدود هذه القواعد
- قواعد Firebase لا تحل محل التحقق داخل Cloud Functions؛ Admin SDK يتجاوز Firestore Security Rules.
- `contentType` يمكن تزويره؛ افحص التوقيع الحقيقي للملف ونفّذ malware scanning قبل إتاحته.
- حدّ الحجم هنا لا يمنع الإساءة بمفرده؛ أضف App Check وحصص/معدلات في backend.
- هذه مراجعة هندسية أولية وليست تدقيقًا أمنيًا مستقلًا أو ضمانًا ضد الاختراق.
